# dzahdev.recom - персональные рекомендации товаров

Дата: 2026-10-22. Статус: дизайн утвержден, план реализации - следующий шаг.

## 1. Задача

Модуль 1С-Битрикс для интернет-магазина (редакции с модулями `sale` и `catalog`), который:

- фиксирует действия покупателей с товарами: просмотр, добавление в корзину, отложенный товар, покупка;
- обучает на этих событиях модели рекомендаций внутри самого модуля, без внешних сервисов, Docker и
  отдельных бинарников;
- выводит персональные рекомендации, похожие товары и популярное.

Ограничение: все в рамках модуля на чистом PHP 8.1+. Установка модуля - стандартная установка из
`/local/modules/` или Маркетплейса, без настройки сервера.

## 2. Модели и первоисточники

Модуль реализует опубликованные математические модели собственным кодом на PHP:

| Компонент модуля | Первоисточник |

| Похожие товары | косинус с весами обратной частоты пользователя (J. Breese, D. Heckerman, C. Kadie, UAI 1998) и сжатием n/(n + 100) (Y. Koren, Factorization Meets the Neighborhood, KDD 2008) |
| Популярное | сумма весов сигналов за окно |
| Цепочка выдачи | персональная подборка -> похожие на последние товары -> популярное (раздел 5.5) |

## 3. Идентификаторы

- ID модуля: `dzahdev.recom`, пространство имен `\Dzahdev\Recom`.
- Таблицы: `b_dzahdev_recom_*`.
- Репозиторий: приватный `dzahdev/bitrix_recom_module`.
- Пользователь: `FUSER_ID` (`\Bitrix\Sale\Fuser::getId()`). Есть у гостей; при первой авторизации
  гостевой `FUSER_ID` привязывается к пользователю (ограничение для пользователя, у которого уже
  есть своя корзина, - в разделе 11). Своя cookie не нужна.
- Товар: ID элемента инфоблока каталога. Торговое предложение сводится к родительскому товару через
  D7: `\Bitrix\Catalog\CatalogIblockTable` (инфоблок предложений и `SKU_PROPERTY_ID`) и значение
  свойства привязки из ORM инфоблоков.

| Настройки | `\Bitrix\Main\Config\Option` | `COption` |
| Журнал | `\Bitrix\Main\Diag\EventLogger` | `CEventLog::Add` |
| Регистрация модуля | `\Bitrix\Main\ModuleManager` | `RegisterModule` |
| Покупатель | `\Bitrix\Sale\Fuser`, `\Bitrix\Sale\Basket`, `\Bitrix\Sale\Order` | `CSaleUser`, `CSaleBasket`, `CSaleOrder` |
| Каталог | `\Bitrix\Catalog\ProductTable`, `CatalogIblockTable`, `PriceTable` | `CCatalogProduct`, `CCatalogSku` |
| Контроллеры | `\Bitrix\Main\Engine\Controller` | `ajax.php` с `$_REQUEST` |

## 4. Сбор событий

Типы событий и их источники:

| Тип | Источник | Условие |
|---|---|---|
| `view` | ORM-события `catalog`: `\Bitrix\Catalog\CatalogViewedProduct::OnAfterAdd` и `::OnAfterUpdate` | запись в `b_catalog_viewed_product` из `CatalogViewedProductTable::refresh()` |
| `cart` | `sale`: `OnSaleBasketItemSaved` | новая позиция корзины, `DELAY = N` |
| `delay` | `sale`: `OnSaleBasketItemSaved` | позиция с `DELAY = Y` |
| `buy` | `sale`: `OnSaleOrderSaved` | новый заказ, событие на каждую позицию |

Для шаблонов, которые не вызывают `CatalogViewedProductTable::refresh()`, есть JS-метод
`DzahdevRecom.trackView(productId)`, который вызывает AJAX-контроллер модуля.

Обработчик события только пишет строку в `b_dzahdev_recom_event`. Расчетов на хите нет.

Настройки: какие типы считаются положительным сигналом для обучения (по умолчанию все четыре) и их
вес (по умолчанию `view` 1, `delay` 2, `cart` 3, `buy` 5).

- ALS и похожие товары работают с бинарной матрицей: пара (пользователь, товар)
  положительна, если по ней есть хотя бы одно событие положительного типа. Вес в эти модели не входит.
- Вес входит в оценку популярного (сумма весов событий за окно) и в порядок последних сигналов
  пользователя для шага 2 цепочки выдачи (сумма весов по товару, затем время).

## 5. Модели

### 5.1 ALS (персональные рекомендации)

Покоординатный спуск для неявных сигналов (eALS с одинаковым весом α неотмеченных пар):

- матрица Грама `S = QᵀQ` по факторам товаров (для шага по пользователям) и `S = PᵀP` (для шага по
  товарам);
- обновление фактора `f` пользователя `u`:
  `p_uf = (a - b) / (c + α·S_ff + λ)`, где
  `a = Σ_i∈R(u) (1 - (1-α)·r̂ᶠ_ui)·q_if`,
  `b = α·Σ_k≠f p_uk·S_kf`,
  `c = (1-α)·Σ_i∈R(u) q_if²`,
  `r̂ᶠ_ui` - предсказание без вклада фактора `f`;
- симметричное обновление факторов товара.

Параметры по умолчанию: 16 факторов, `λ (reg) = 0.06`, `α (weight) = 0.001`,
начальное распределение N(0, 0.1). Число эпох полного обучения - 20, дообучения - 3.

Оценка пары: `score(u, i) = p_u · q_i`.

### 5.2 Похожие товары

Множество пользователей с положительным сигналом по товару. Расстояние = 1 - (косинус с весами IDF) ·
n/(n + 100) (раздел 2):

- если множества совпадают - 0;
- если есть общие пользователи - `1 - Σidf(common)·n / (√Σidf(A) · √Σidf(B) · (n + 100))`, где
  `n` - число общих пользователей, `idf(u) = log(N_items / N_items(u))`;
- если общих нет - 1.

Для каждого товара хранится top-K (по умолчанию 20) ближайших.

### 5.3 Популярное

Сумма весов положительных сигналов за окно (по умолчанию 30 дней), общий рейтинг и рейтинг по
каждому разделу каталога. Хранится top-K (по умолчанию 100).

### 5.4 Ранжирование FM (минимальная версия)

Классическая factorization machine по статье S. Rendle, "Factorization Machines", ICDM 2010, без
собственных изменений модели: уравнение модели второго порядка (раздел III-A), вычисление
попарных взаимодействий за `O(k·n)` (лемма 3.1), обучение SGD с L2-регуляризацией (раздел III-C),
логистическая потеря для бинарной классификации (раздел III-B). Единственное, что добавляет модуль, -
подготовка данных: без записи показов класс 0 получается выборкой случайных товаров без сигнала
(стандартный прием для неявных сигналов). Признаки бинарные, `xᵢ ∈ {0, 1}`:

- признаки пары: покупатель (`FUSER_ID`), товар, основной раздел товара (`IBLOCK_SECTION_ID`,
  пропускается для товара без раздела);
- оценка: `y = w₀ + Σᵢ wᵢ + ½·Σ_f [(Σᵢ v_if)² - Σᵢ v_if²]` по активным признакам;
- обучающие примеры: каждая положительная пара из раздела 4 с меткой 1 и `fm_negatives`
  (по умолчанию 2) случайных товаров без сигнала от этого покупателя с меткой 0;
- шаг SGD при `g = σ(y) - метка`: `w₀ -= η·g`, `wᵢ -= η·(g + λ·wᵢ)`,
  `v_if -= η·(g·(Σⱼ v_jf - v_if) + λ·v_if)`;
- параметры по умолчанию: 8 факторов, `η = 0.05`, `λ = 0.0001`, 30 эпох, начальное распределение
  N(0, 0.01); 30 эпох выбраны замером на стенде (38 товаров, 200 покупателей): при 10 эпохах
  NDCG@10 около 0.25 (недообучение), при 30, 50 и 100 - около 0.6;
- модель обучается заново при каждом прогоне и не хранится: она нужна только при подготовке подборок.

Раздел как признак дает оценку и товару без собственной истории: новый товар в разделе, который
покупатель выбирает, получает высокую оценку через вектор раздела.

Роль в выдаче: при `fm_enabled = Y` (по умолчанию) кандидаты персональной подборки ранжируются FM,
иначе ALS. При полном обучении на отложенной выборке считаются оба NDCG@10, и оба выводятся в
админке - по ним решается, держать ли FM включенной на данных конкретного магазина.

Вне минимальной версии: цена и свойства инфоблока как признаки, учет показов блоков и кликов,
хранение FM между прогонами.

### 5.5 Цепочка выдачи для пользователя

1. Персональная подборка (кандидаты из соседей товаров пользователя и популярного, ранжирование FM
   или ALS по разделу 5.4), если у пользователя не меньше `minUserEvents` положительных сигналов
   (по умолчанию 3) и он присутствует в модели.
2. Иначе - похожие на товары из его последних сигналов.
3. Иначе - популярное.

Из выдачи исключаются купленные товары, товары в корзине, неактивные и недоступные к покупке.
Переход по цепочке - часть логики рекомендаций для пользователей с короткой историей, а не обработка
ошибок: сбой обучения пишется в журнал событий (`\Bitrix\Main\Diag\EventLogger`) и показывается в админке, выдача при
этом использует последнюю успешно обученную модель.

## 6. Обучение

- Консольный скрипт модуля `php local/modules/dzahdev.recom/tools/train.php [--full]` из корня сайта:
  только PHP CLI, без composer; код выхода 0 - успех, 1 - ошибка. Для сайтов с Symfony Console
  (composer) та же операция доступна командой `php bitrix/bitrix.php dzahdev.recom:train [--full]`
  (секция `console` в `.settings.php`): `bitrix.php` без composer не запускается, поэтому основной
  путь - скрипт.
- Агент `\Dzahdev\Recom\Agent\TrainAgent::run()` для сайтов с агентами на cron. Обучение
  выполняется только при `BX_CRONTAB === true` или в CLI; на хите агент пропускает обучение и
  пишет предупреждение в журнал.
- Дообучение (по умолчанию раз в час): ALS стартует с сохраненных факторов, 3 эпохи; новые
  пользователи и товары получают случайные начальные факторы.
- Полное переобучение (по умолчанию раз в сутки): ALS с нуля, 20 эпох, пересчет похожих товаров
  и популярного, пересчет готовых подборок.
- Блокировка от параллельного запуска - через `\Bitrix\Main\Application::getConnection()->lock()`.
- Качество: NDCG@10 на отложенной выборке (последний положительный сигнал каждого пользователя)
  для ALS и для FM, сохраняется с результатом обучения.
- FM (раздел 5.4) обучается при каждом прогоне после ALS, если `fm_enabled = Y`.

## 9а. Рекомендации в письмах

Компонент `dzahdev:recom.list.mail` для почтовых шаблонов Битрикса (стандартная отправка через
почтовые события `\Bitrix\Main\Mail\Event`). Вызов в тексте HTML-шаблона письма:

```php
<?EventMessageThemeCompiler::includeComponent("dzahdev:recom.list.mail", "", Array(
	"MODE" => "personal",
	"USER_ID" => "{#USER_ID#}",
	"COUNT" => "4",
))?>
```

Компилятор шаблона превращает макрос `#USER_ID#` в `$arParams["USER_ID"]`, поэтому в параметр
попадает значение поля письма (так же работает `bitrix:sale.bigdata.personal.mail`).

- Параметры: `MODE` (`personal`, `similar`, `popular`), `USER_ID` (для `personal`), `PRODUCT_ID`
  (для `similar`, например `{#PRODUCT_ID#}`), `SECTION_ID` (для `popular`), `COUNT`.
- В письме нет текущего посетителя: покупатель определяется по `USER_ID` чтением
  `\Bitrix\Sale\Internals\FuserTable` без создания новой записи. Нет `USER_ID` или у пользователя нет
  корзины покупателя - выдача популярного (истории нет).
- Список берется из той же цепочки выдачи (раздел 5.5) с сайтом письма для исключения корзины,
  затем фильтруется по `\Bitrix\Catalog\ProductTable`: элемент активен и `AVAILABLE = Y`; в письмо
  идут первые `COUNT` товаров.
- Отрисовку выполняет стандартный `bitrix:catalog.show.products.mail` (параметр `LIST_ITEM_ID`):
  верстка для почтовых клиентов, абсолютные ссылки и цены для группы "все пользователи" остаются
  на стороне ядра, как у `sale.bigdata.personal.mail`.
- Пустой список - компонент ничего не выводит, письмо уходит без блока.

## 10. Проверка

- Модульные тесты чистой математики без Битрикса (`tests/run.php`, стиль `dzah.hotclient`):
  - ALS на синтетических данных с известной блочной структурой: NDCG@10 после обучения выше
    случайного порога;
  - FM: формула оценки на заданных весах; на синтетике с разделами персональная выдача держится
    своего раздела, новый товар без истории получает более высокую оценку у покупателей его раздела;
  - формула похожести сверена с тестовыми значениями `logics/item_to_item_test.go`;
  - упаковка и распаковка векторов без потерь.
- Замер: обучение на 100 000 синтетических событий (5 000 пользователей, 1 000 товаров) - время и
  память фиксируются в спецификации плана.
- Сквозная проверка на локальном стенде с демо-магазином: просмотр, корзина, заказ дают события;
  после обучения выдача персонального блока отличается от популярного.
- Письмо: тестовое почтовое событие с компонентом `dzahdev:recom.list.mail` отправляется через
  `\Bitrix\Main\Mail\Event::sendImmediate`, в Mailpit стенда письмо содержит карточки товаров с
  абсолютными ссылками.

## 11. Вне объема

- FM сверх минимальной версии: цена и свойства инфоблока как признаки, учет показов и кликов,
  механизм внимания (attentional FM).
- Рекомендации на основе эмбеддингов и LLM.
- Многосайтовость с раздельными моделями (поле `SITE_ID` хранится, модель общая).
- A/B-тесты выдачи.
- Перенос истории гостя при входе: если у пользователя уже есть своя корзина покупателя, Битрикс при
  авторизации переносит в нее позиции гостевой корзины, а события, записанные под гостевым
  `FUSER_ID`, остаются за ним. Объединение историй - кандидат на следующую версию.
